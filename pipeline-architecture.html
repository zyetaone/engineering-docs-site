Pipeline architecture

How a change moves from a branch to a published release and a live website, which gate blocks it at each step, and what each gate is actually proving. The canonical rules for contributors live in CONTRIBUTING.md; this document is the operator's map.

Rendered version with diagrams: index.html. The diagram sources are in ../diagrams/ and are built by node enterprise/diagrams/build.mjs.

Two design decisions are worth keeping in mind when you change a job name:

  1. Aggregator jobs exist so a required check is always present. webm-artifact is required; the two jobs it aggregates are conditional. A required check that is skipped leaves a pull request permanently pending, so the aggregate always runs and fails when a dependency failed or was skipped unexpectedly.
  2. The classifier is allowed to ask for more, never less. An empty diff, an unknown path or an unavailable comparison base all select full coverage. A failed classification cannot become a successful skip.

Promotion path

dev is the integration branch, main is stable. A change lands on dev, gets used on real diagram tasks, and is promoted to main in a separate pull request that records the tested revision and any unresolved issue. Passing CI is not trial-use acceptance; CONTRIBUTING.md owns that distinction and this pipeline does not try to encode it.

Publication is a tag on main, not a merge. That separation is why a rollback is cheap: the site can be reverted with a commit, a release can be superseded with a new tag, and neither requires unpicking a deploy pipeline.

A pull request never sees a production secret: environment secrets are only released to a job that declares the environment, and no pull_request job here declares one. That is also why preview uses its own environment rather than borrowing the production one.

Token permissions

  • Every workflow declares a top-level permissions: block, defaulting to contents: read. A job opts in to more (pages: write, security-events: write, contents: write for a release) only where it needs it.
  • No workflow uses permissions: write-all.
  • persist-credentials: false is set on checkouts that do not need to push.

What is deliberately absent

  • No merge queue. The ruleset's strict_required_status_checks_policy already requires an up-to-date branch; a queue would add a second, weaker truth.
  • No self-hosted runners. Nothing here needs one, and a self-hosted runner on a public repository is a standing invitation.
  • No auto-merge. repository.json disables it, so no bot or agent can arm a merge and let it complete unattended.
  • No second release pipeline. provenance.yml describes published bytes; it never builds or uploads archify.zip. CONTRIBUTING.md is explicit that the existing release gates are reused rather than duplicated.
  • No deploy from a pull request. Previews publish to a preview branch; the production branch is only reachable from main after every gate.
